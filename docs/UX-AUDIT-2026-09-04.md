# WeCare — UX Audit (code + docs review)

**Date:** 2026-09-04 · **Branch:** `audit-fixes` · **Against:** the Product Owner UX Master Brief (68 sections).

## Method & limitations

This is a **code + documentation + shared-screenshot** review, not a live-usability audit. The Claude-in-Chrome extension is not connected in this session, so the brief's prescribed methods could **not** be run:

- §7 — walk the rendered site as a user
- §50–53 — first-time-user / four-journey / beginner-vs-experienced persona walkthroughs
- §63 — real-device QA (iPhone SE, 14/15-class, mid Android, iPad)
- §66 — final blind acceptance test

Everything below is assessed from: the source (all routes, components, i18n, recommendation logic), the decision history (`CLAUDE.md`, `docs/*`), and the screenshots shared during this session. **Findings about "how it feels" carry lower confidence than findings about "what the code does."**

## Executive summary

**Verdict: READY WITH CONDITIONS.**

The product already implements the large majority of the brief — problem-first architecture, the four problems, a 6-question auto-advancing assessment that reads as a quiz not a form, the beginner-simplified recommendation page (one primary card, THC behind an accordion, alternative demoted), progressive disclosure, Solution-over-strain identity, honest gating of every piece of missing real-world data, and (this session) mobile button widths, shipping-address capture, and removal of fabricated legal/company/delivery claims.

**The conditions are almost entirely "not verifiable in this session":**

1. **No live accessibility audit** — contrast, keyboard traversal, screen-reader names, focus order (P2, needs a browser).
2. **No real-device mobile pass** — above-the-fold priority, tap-target spacing, German line-length overflow on 320 px (P1 for launch, needs hardware — this is the standing D25 blocker).
3. **Analytics measures nothing yet** — the funnel is fully instrumented but `dispatch()` is empty; no PostHog EU account (P2, procurement).
4. A short list of P2/P3 items below.

**No P0 found** (no surface where the core journey is broken). Code-actionable findings resolved 2026-09-04: **UX-01** (the "7/10" hero label — removed), **UX-06** (postcode-step framing — Option 1, reframed as a lead-in), plus **CheckoutSteps** "Review" step. **UX-07** was withdrawn on re-check (q5 hints already exist). The rest of P1 is the device-QA blocker.

## Issues (ranked)

### UX-01 · Homepage · P2 · "7/10" decorative label on the hero ring — ✅ FIXED (2026-09-04)
- **Problem:** the hero's `AssessmentRing` showed `startLabel="7/10"` with trail dots. It read as a real assessment score for a user who hadn't taken the assessment.
- **Fix:** dropped the `startLabel` prop from the homepage hero `AssessmentRing`. The arc + trail dots still signal "the quiz" without asserting a number. `src/pages/home/sections.tsx`; comments + CLAUDE.md updated.

### UX-02 · Site-wide · P2 (needs browser) · No live accessibility audit
- **Problem:** WCAG 2.2 AA (§41) has never been checked against the rendered site — contrast ratios (esp. white/70–80 text on the brand gradient heroes, `text-ink-muted` on glass), keyboard-only traversal of the assessment / accordions / dashboard tab bar, focus order, screen-reader names on icon-only controls, error-to-field association outside checkout.
- **User impact:** unknown; potentially blocking for users with low vision or who navigate by keyboard/SR.
- **Evidence:** foundations exist (`common:a11y.skipToContent`, `aria-label` on cart/qty buttons, `aria-invalid`/`aria-describedby` on checkout, `motion-reduce:` utilities) but no audit artifact.
- **Recommendation:** run axe (or Lighthouse a11y) on the 8 critical surfaces + a manual keyboard and VoiceOver/NVDA pass on the assessment and dashboard. Fix contrast tokens if any hero text falls below 4.5:1.

### UX-03 · Mobile · P1 (needs hardware) · No real-device QA
- **Problem:** §37 (tap-target size/spacing), §38 (above-the-fold priority per surface), §42 (German overflow) are all unverified on physical phones. This is the standing **D25** blocker.
- **User impact:** most acquisition traffic is expected to be mobile; unknown layout/touch defects on the highest-traffic surface.
- **Evidence:** responsive classes are present and this session added `w-full sm:w-auto` to standalone buttons; the assessment auto-advances; the dashboard has a mobile app-shell. But no device-matrix pass.
- **Recommendation:** the D25 matrix — iPhone SE, a 14/15-class device, a mid-range Android, an iPad — walking homepage → each problem page → assessment → recommendation → solution → review → (gated) checkout → dashboard. 2–3 working days, final QA week.

### UX-04 · Site-wide (DE) · P2 · German line-length risk unverified
- **Problem:** DE strings run longer than the EN placeholders the layouts were built against. Candidates: the four identical problem CTAs "Jetzt unverbl. Fragebogen starten", `checkoutSteps` labels + "· Fertig" on a 320 px bar, accordion trigger labels, dashboard `HeroCta` labels (already `truncate`), condition-page headings.
- **User impact:** truncated or awkwardly-wrapped CTAs and labels on small screens erode the "premium, calm" feel and can hide the action.
- **Evidence:** no browser check possible; `truncate` is applied in a few known-risky spots but not systematically.
- **Recommendation:** part of UX-03's device pass — specifically eyeball every button/label in DE at 320 px; add responsive text sizing or `min-w-0` / `break-words` where it breaks.

### UX-05 · Analytics · P2 (procurement) · Nothing is being measured
- **Problem:** the whole funnel is instrumented (`track()` at every §46 point, with `device_class`, `traffic_source`, `funnel_version`, and D16 data-minimisation), but `dispatch()` in `src/lib/analytics.ts` is empty — no vendor. None of the §47 recommendation-page metrics are collected.
- **User impact:** none directly; but every §48 experiment and every funnel-drop decision is currently blind.
- **Evidence:** `analytics.ts` `dispatch()` is a no-op; `.env.example` has empty `VITE_POSTHOG_*`.
- **Recommendation:** company-owned PostHog EU account → wire `dispatch()` → verify the recommendation-page events fire with `device_class` + `traffic_source`. Required before paid acquisition (per PO decision set 3).

### UX-06 · Assessment · P3 · Two pre-question steps before "the 6 questions" — ✅ Option 1 done (2026-09-04)
- **Problem:** the promised flow is "6 questions, 60–90 s". The actual sequence is **Age gate → Postcode → Q1…Q6**. A beginner taps through two gates before the quiz they were promised.
- **PO ruling:** Option 1 (reframe as a lead-in) now; Option 2 (move the postcode step after the assessment) queued as a §48 A/B for when analytics is live.
- **Done:** `AssessmentEnginePage` — during the postcode phase the eyebrow is now **"Getting started · One quick delivery check, then your questions"** (`phase.leadIn` / `phase.leadInNote`), not "Your assessment · Question 1", so the two pre-steps read as a one-off setup, not numbered questions. The age gate already framed itself well ("First, a quick confirmation" / "Continue to the assessment") — unchanged. Dead `phase.delivery` / `phase.finalChecks` keys removed.

### UX-07 · Assessment · P3 · q5 format terms — ⛔ WITHDRAWN (2026-09-04)
- Re-checked against `assessment.json` (EN + DE): q5 **already has** hints for `oil` / `flowers` / `vape` ("Drops taken by mouth", "Dried plant material, inhaled", "Inhaled as vapour from a pen or device"), and `QuestionStep.tsx` renders them. The original finding was based on an incomplete dump. No change needed.

### UX-08 · Homepage · P3 (experiment candidate) · Rotating hero headline
- **Problem:** the hero's second line is a `RotatingWord` cycling Sleep/Pain/Stress/Migraine. It's `aria-hidden` with an `sr-only` static sentence and a reduced-motion fallback, so it's accessible — but for the "understand within seconds" test (§8/§50) a moving headline is a comprehension variable.
- **User impact:** low; possibly a slight first-glance parse cost.
- **Evidence:** `RotatingWord.tsx`; CLAUDE.md homepage §1.
- **Recommendation:** keep for now; log it as the §48 A/B (rotating vs. static headline) to run once analytics is live. Don't change blind.

### UX-09 · Checkout · P2 (data-blocked) · No checkout experience to evaluate
- **Problem:** `PRICES_CONFIRMED = false` → `COMMERCE_ENABLED = false` → `/dashboard/checkout` renders the `checkoutUnavailable` panel; cart shows `finalPriceNote` and no CTA; the Solution page shows `orderingDisabledNote`. This is the **correct honest state**, but it means §29's checkout criteria (fee lines, payment timing, summary) cannot be assessed against a live flow.
- **User impact:** none now — the gated copy is clear about why.
- **Evidence:** `src/config.ts`; `CheckoutPage.tsx` gated early-return.
- **Recommendation:** none this session — re-audit checkout the moment real pharmacy prices land and `PRICES_CONFIRMED` flips. The form code (first/last name, inline validation, `CheckoutSteps`, transparent fee rows) is already built behind the gate.

### UX-10 · Review status / Dashboard · P3 (backend-blocked) · Status never progresses
- **Problem:** `submitMedicalReview()` writes `inReview` and nothing advances it (no backend, and the demo override was reverted). A user who submits sees "In medical review" indefinitely.
- **User impact:** none for a real launch (a real doctor moves it); noticeable only in demos/stakeholder review.
- **Evidence:** `src/features/review/review.ts`.
- **Recommendation:** none for production. For demos, a scoped, clearly-labelled status stepper could be added behind a flag — but that's dev scaffolding, which the PO asked to keep out.
